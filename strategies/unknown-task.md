# Unknown Task Mode — 예상 밖 과제 대응

> **대상: Codex 참고 — 지시가 아니다.** 지시는 과제 루트의 `AGENTS.md`와 `CONTRACT.md`가 우선한다. 런북 프롬프트가 이 파일 경로를 지정할 때만 읽는다.

> **목적:** 7개 유형(A–G)에 맞지 않는 문제를 억지로 분류하지 않고, 180분 내 검증 가능한 산출물을 만든다. 이 문서는 새로운 에이전트 조직이나 기술 스택을 강제하지 않는다.

## 작동 조건
- 과제가 A–G 중 어느 하나에도 깔끔하게 들어맞지 않는다.
- 산출물은 익숙하지만 핵심 알고리즘/도메인이 생소하다.
- 다중 형태 과제(예: 시뮬레이션 + UI, API 통합 + 데이터 정제)여서 기존 전략 둘로도 불충분하다.
- 평가 방식이 예상과 다르다(예: 화면이 아닌 CLI, 동작하는 게임, 기존 코드의 테스트 통과, 수치 모델 결과).

## 5개 질문으로 재분류 (T+0~10분)
1. **Deliverable:** 필수 출력은 무엇인가? (실행 프로그램, UI, API, 파일, 보고서, 테스트 통과 등)
2. **Inputs:** 실제 제공된 것은 무엇인가? (데이터, 소스, 문서, 이미지, API, 설정)
3. **Oracle:** 성공을 어떻게 *검증*하는가? 명시 테스트/스키마/지표가 없으면 최소 검증 기준을 제안한다.
4. **Hard constraints:** 반드시 지켜야 할 제한, 포맷, 자원, 권한은 무엇인가?
5. **First proof:** 30~45분 내 확인할 최소 동작 예시는 무엇인가?

**과제 도메인과 출력 형태를 분리한다.** 최적화 과제라도 출력은 UI일 수 있고 RAG 과제라도 CLI만 요구될 수 있다. Auth·UI·DB를 요청받지 않았다면 자동으로 만들지 않는다.

## 기본 실행 구조
- 기본은 한 Codex 세션이 처음부터 검증까지 맡는다.
- **허용되는 분할 1건 — 생소한 도메인·API 조사:** 처음 보는 도메인·라이브러리·API의 사용법이 첫 결과를 막을 때. 사람이 Terminal 2에서 `~/playbook/prompts/specialist-research.md`로 두 번째 세션을 띄운다. 읽기 전용이고 결과는 과제 루트 `RESEARCH.md` 한 파일, 10분 안에 끝낸다. Main은 그동안 기계적인 작업을 진행하고, 끝나면 그 파일을 읽어 반영한다.
- 그 밖의 역할 분할(Frontend/Backend/QA 등), 구현 분할, Codex가 스스로 에이전트를 띄우는 것은 하지 않는다.
- 복잡한 새 도구 설치보다 기본 언어·표준 라이브러리와 제공 환경의 기능을 우선한다.

## 실행 프로세스
> 시간 구간은 런북 B 프롬프트(B1~B5)와 같다. 다르면 런북을 따른다.

### 0–10분: 계약 추출 (런북 프롬프트 1에서 이미 끝났으면 건너뛴다)
- README에서 **필수 산출물 및 평가 가능 조건**을 직접 인용 가능한 수준으로 추출한다.
- 익숙하지 않은 전문 용어는 최소 정의만 확인한다.
- 답에 실질적 영향을 미치는 모호함만 업무 담당자에게 질문한다.
- **실행할 필요가 없는 것**도 정한다: Auth, UI, DB, MCP, 배포, LLM API 등.

### 10–25분: 기술 가능성 검증
- 선택한 언어와 핵심 라이브러리의 실행, 파일 읽기/쓰기, API 접근을 작은 스파이크(spike)로 확인한다.
- 전체 문제 대신 **가장 위험한 한 가지 가정**만 실험한다.
- 라이브러리 설치·외부 연결 실패가 5분 정도 반복되면 fallback으로 전환한다(Skill·MCP는 설치하지 않는다). 이 시간은 절대 규칙이 아니라 병목 방지 기준이다.

### 25–45분: 첫 검증 가능한 결과
- 하나의 입력에 대해 기대 형태의 출력을 생성한다. 처음에는 단순한 baseline 또는 일부 범위만 지원해도 된다.
- 최소 검증기(스키마, 제약, 테스트, 지표)를 동시에 준비한다.
- 즉시 재실행 가능한 명령을 기록한다.

### 45–70분: End-to-end 확장
- 실제 제공 데이터 또는 실제 테스트로 전체 입출력 경로를 한 번 통과한다.
- 불확실성이 남으면 완성도 높은 한 경로를 확보하고 범위를 좁힌다.

### 70–135분: 핵심 품질 개선
- 가장 큰 평가 지표를 개선한다. 추측으로 기능을 추가하지 않는다.

### 135–150분: 검증·안정화
- Hard constraints, 핵심 테스트, 실패 케이스, 재현성 검사.
- 새로운 의존성/기능/대규모 리팩터링 금지.

### 150–170분: 제출 문서·제출 준비
- SUBMISSION.md 작성, 필수 경로·실행 명령·결과물·저장 상태 점검. T+170 제출 미리보기 착수 권장.

## 실패 신호와 즉시 전환
| 신호 | 바로 할 행동 |
|---|---|
| 10분이 지나도 유형 논쟁만 지속 | 유형 분류 포기; 산출물·입출력·검증을 기준으로 최소 구현 결정 |
| 25분에도 실행할 방법을 못 찾음 | 외부 설치·MCP 탐색 중단, 가장 단순한 지원 환경으로 전환 |
| 45분에도 샘플 입력→출력이 없음 | 품질 개선 중단, 1개 사례만 통과하도록 범위 축소 |
| 70분에도 전체 흐름이 없음 | 새 아키텍처 중단, 연결 복구를 최우선으로 |
| 도메인 모호성이 업무 정책을 바꿈 | 업무 담당자에게 1~3개 결정적 질문, 임시 가정 명시 |
| Codex Capacity 오류 | 응시자가 처리한다(모델 전환·상태 복구). 재개되면 `CONTRACT.md`·`DECISIONS.md`를 읽고 미완료 AC부터 이어서 한다 |

## 예상 밖 사례별 첫 구현
| 실제 문제 예시 | 첫 증거 | 피할 일 |
|---|---|---|
| 게임/강화학습 에이전트 | baseline policy가 1회 환경 실행·점수 출력 | 웹 로그인 구현 |
| 물리/과학 시뮬레이션 | 작은 입력에서 수치 결과·단위 테스트 | 대시보드부터 제작 |
| 외부 API 연결 | 실제 호출/인증/응답 스키마 최소 검증 | 대규모 UI 구축 |
| 프론트엔드 전용 | 주어진 화면/상호작용 하나 동작 | 불필요한 DB 도입 |
| 보안 감사 | 재현 가능한 취약 테스트와 최소 패치 | 전면 리팩터링 |
| 멀티모달 처리 | 샘플 한 건 추론·출력·검증 | 자원 확인 없는 대형 모델 설치 |
| 기존 시스템 수정 | 현재 실패 재현→최소 패치→회귀 테스트 | 새 프로젝트 생성 |

## 마무리 원칙
'새 유형을 찾아냈다'가 아니라 '증명 가능한 입력→출력 흐름을 확보했다'를 진척으로 판단한다. 초반 전략이 틀렸다는 증거가 생기면 문서의 분류보다 실제 테스트 결과를 우선한다.
