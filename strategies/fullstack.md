# 전략 A — Full-stack 업무 서비스

> **대상: Codex 참고 — 지시가 아니다.** 지시는 과제 루트의 `AGENTS.md`와 `CONTRACT.md`가 우선한다. 런북 프롬프트가 이 파일 경로를 지정할 때만 읽는다.

**적용:** 경로 B-웹(스택·스타터가 지정된 웹, 또는 로그인·저장 없는 단순 웹). 경로 A(boilerplate 사용)에서는 `web/BOILERPLATE.md`가 이 역할을 하므로 이 문서를 읽지 않는다. OR이 있으면 `optimization.md`도 읽는다.

## 작업 방식
한 Codex 세션이 처음부터 검증까지 맡는다. 이 유형에서는 분할하지 않는다(구현을 여러 세션에 나누면 통합 비용이 이득보다 크다).

## 구축 순서
1. 원본 데이터 스키마와 사용자 여정 확정. 요구사항에 역할이 없다면 Auth를 억지로 추가하지 않는다.
2. 과제가 지정한 스택·스타터를 그대로 쓴다. boilerplate는 반입하지 않는다(사용 여부는 CONTRACT 9절에서 이미 결정됨). 로그인이 필요하면 `/tmp/ref_web/lib/auth/`와 `/tmp/ref_web/lib/http.ts`의 패턴만 이식한다. 새 라이브러리는 필요할 때만 추가한다.
3. `로그인(필요 시) → 서버 권한 검사 → DB 쓰기/읽기 → 화면`의 **하나의 수직 기능**을 먼저 완성.
4. 핵심 도메인 기능 연결 후 목록/상세/결과와 기본 오류 메시지 구축. 미관보다 동작과 접근 제어.
5. CSV·파일 가져오기는 실제 과제가 요구할 때만. 샘플 데이터에 하드코딩하지 않는다.

## 필수 검증
- 보호된 API 미로그인 접근 차단, 일반 사용자 관리자 API 접근 차단, 다른 사용자 데이터 접근 통제.
- 서버 입력 검증(잘못된 입력은 400), DB 저장 후 새로고침에도 유지, 에러 응답.
- 지정 스택의 빌드·테스트 명령과 핵심 API curl 확인(CONTRACT 9절 검증 명령).
- 웹 서버는 `0.0.0.0`로 실행하고 내부 Browser에서 포트/경로 확인.
